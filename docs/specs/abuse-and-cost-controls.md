# Abuse and cost controls — specification

**Status:** Proposed

**Owner:** Finntegrate

**Related architecture:** [ADR 0009](../ADRs/0009-abuse-and-cost-controls.md), [ADR 0008](../ADRs/0008-auth-and-tenancy.md), [ADR 0010](../ADRs/0010-server-held-conversation-history.md)

## Problem statement

Anonymous access puts a paid language model behind a public endpoint. The principal threat is denial of wallet: an unbounded bill that forces the service off. Related threats are floods from many actors at once, a leaked access code, runaway agent loops, prompt-injected spending, and guessing access codes. Controls must hold without identifying anyone, must not penalize people who share a network address, must not be noticeable in ordinary use, and must never stand between a person in crisis and emergency help. The decision and its rationale are in [ADR 0009](../ADRs/0009-abuse-and-cost-controls.md); this document is the mechanism.

## Goals

1. Total spend has a ceiling that holds even if this service's code is wrong.
2. The maximum rate of spend is a number calculated from configuration, with no observed quantity in it.
3. No single request, session, or code can consume a meaningful share of either.
4. Ordinary users, including those behind shared addresses, see at most a short wait.
5. Every refusal or failure a person can see includes emergency help.
6. The beta controls need no new service or paid infrastructure.

## Non-goals

- **Identifying abusers.** Controls act on codes, sessions, and spend, and keep no durable record of who was limited.
- **Defeating a well-funded distributed attacker.** The ceiling bounds the cost of one; nothing here prevents one from reaching it.
- **Content abuse.** Sensitive and off-topic queries are handled by [the guardrails policy](guardrails.md).
- **Billing.** These are cost controls, not paid tiers.

## Threats and the controls that answer them

| Threat | Primary control | Backstop |
| --- | --- | --- |
| Volumetric flood | Hosting provider edge | Request size limits |
| Many actors at once | Turn-start rate and concurrency limit | Provider spend ceiling |
| Disconnecting to churn turns | Turn-start rate; places held until model calls end | Per-session limits |
| Mass session creation | Access codes and per-code session limits | Per-address limits |
| A leaked code | Per-code turn budget and capacity share | Alerting, stopping admission, ending sessions |
| Guessing access codes | Code entropy | Entry-form rate limits |
| One expensive request | Request bounds | Turn-start rate |
| Forged or inflated history | [Server-held history](conversation-history.md) | Input bounds |
| Agent loop or injected tool use | Step, model-call, and tool-call bounds | Turn timeout |
| Paid tool spend | Paid tools off | Kill switch |

## Emergency line

Every message the service shows instead of an answer carries a fixed emergency line: 112 and the approved general crisis entries from the [crisis and escalation resources](crisis-escalation-resources.md). The line is stored and translated with the other user-facing strings and is never generated by a model. It appears on:

- the access-code page, before a person has a code,
- every refused code,
- every rate-limit, busy, and queue-full message,
- the closed state,
- a turn stopped by a bound before it could answer.

A turn whose guardrail classification has matched `crisis` or `legal_sensitive` always delivers its fixed resources, with the fixed introduction if the generated one is not available, even if a bound fires after the match ([guardrails](guardrails.md), [conversation history](conversation-history.md#lifecycle)).

## Access codes

During the beta, an anonymous session is issued only on redeeming a valid access code ([auth and tenancy](auth-and-tenancy.md#anonymous-sessions)).

### Format

A code is 16 characters from Crockford's base32 alphabet, giving 80 bits of entropy, displayed in four groups of four (`XXXX-XXXX-XXXX-XXXX`). Entry is case-insensitive, ignores hyphens and spaces, and maps the commonly confused characters (`O` to `0`, `I` and `L` to `1`). At 80 bits, guessing is infeasible at any rate the entry form permits; the rate limits below exist to stop a guessing campaign consuming capacity, not to make guessing hard.

A code can also be distributed as a link that carries it in the URL fragment (`/join#XXXX-XXXX-XXXX-XXXX`). Browsers do not send the fragment to the server, so the code stays out of access logs, proxy logs, and referrer headers. The page reads it, removes it from the address bar and browser history with `history.replaceState`, and submits it in a request body.

### Generation and storage

Codes are generated by an operator command using the operating system's cryptographically secure random source. The command prints the code once and writes only this record to the identity store ([auth and tenancy](auth-and-tenancy.md#storage)):

| Field | Purpose |
| --- | --- |
| `code_id` | Random identifier used everywhere else |
| `code_hash` | HMAC-SHA-256 of the normalized code, with the [key](auth-and-tenancy.md#keys) version |
| `partner_id` | The issuing partner; see [auth and tenancy](auth-and-tenancy.md#partner-affiliation) |
| `label` | Operator note, for example the cohort or event |
| `expires_at` | Optional; after it, the code admits no new sessions |
| `max_sessions` | Total sessions the code may ever admit |
| `max_sessions_per_day` | Sessions admitted per rolling day |
| `max_turns_per_day` | Turns, across all the code's sessions, per rolling day |
| `max_share` | Largest fraction of the concurrency limit the code's sessions may hold at once; initially 25% |
| `admitting` | Whether the code admits new sessions |
| `sessions_ended_at` | Set when the operator ends the code's sessions |

Counters for sessions admitted and turns per day are kept in the same store, so a restart or a crash does not reset them. Changes from the operator command take effect on the next request. The plain code is never stored, logged, or recoverable; a lost code is replaced, not retrieved.

Codes are issued per partner, or per cohort within a partner, never per person.

### Redemption

The code is submitted in the body of a request to the admission endpoint. The server normalizes it, computes the HMAC, and looks up the hash. Because lookup is by keyed hash, there is no string comparison whose timing depends on the stored code.

On success, the server issues an anonymous session that records the `code_id`. The `code_id` on a session is used only for per-code limits and revocation. Per-code figures are seen only by Finntegrate operators.

A code is refused if it is unknown, not admitting, expired, or past a session limit. Every refusal returns the same response: "This code isn't working. Check it, or ask the organization that gave it to you", followed by the emergency line. The response does not say which condition applied, and takes the same time whichever it was.

### Stopping a code

An operator has two actions, so that dealing with a leaked code does not cost its legitimate users their conversations.

- **Stop admitting** (the default response to a leak): the code admits no new sessions. Sessions it already admitted continue until their own expiry. Expiry of the code has the same effect.
- **End sessions** (for a code being actively abused): every session the code admitted is refused on its next request, with a message that access has ended and how to get a new code. Its conversations are kept until their normal expiry. Redeeming a new code in the same browser restores the session, with its cookie and conversations, under the new code.

### Entry-form safeguards

- Attempts are limited per network bucket: 60 per minute and 600 per hour, initially, which a partner's group session on one network will not reach.
- Failed attempts are counted across the whole service, and a rate above a configured baseline raises an alert.
- Codes are never locked after failed attempts. Locking would let anyone who knows a code exists deny it to its partner; limiting the source of attempts does not.
- The form has no field other than the code, and is protected by the same-origin rules of the rest of the API ([auth and tenancy](auth-and-tenancy.md#web-security)).

## Spend ceiling

The ceiling is a monthly limit that the model provider enforces by refusing calls: a hard spend cap, or prepaid credit with automatic top-up off. A provider that only sends budget alerts, or enforces its limit with a lag long enough to overshoot materially, does not satisfy this, and is not used for the beta.

- Finntegrate is alerted at 50% and 80% of the ceiling, and on any day whose spend exceeds the ceiling divided by the number of days in the month. Provider usage figures can lag by minutes to hours, so these alerts use the service's own per-turn token counts as well as the provider's.
- When the provider refuses a call for exceeding its limit, the service enters the closed state rather than returning a generic error.

## Maximum spend rate

The turn-start rate and the request bounds together fix the most the service can spend per hour, from configuration alone:

```text
max spend per hour = turn_start_rate_per_minute × 60
                   × max_model_calls_per_turn
                   × max_cost_per_call

max cost per call  = max_input_tokens × input_price
                   + max_output_tokens × output_price
```

`max_input_tokens` is the largest input any call in a turn can send: the system prompt, the guide's prompt, the retrieved passages (the retrieval count times the largest chunk), the history window, the message, and the results of the turn's tool calls (the tool-call bound times the tool-result bound), or the guardrail classifier's prompt and examples with the message if that is larger. Each component has its own configured bound, and their sum is checked at startup.

The worst case for one code is computed the same way, from `max_turns_per_day`.

`turn_start_rate_per_minute` is chosen so that the maximum rate, sustained, would take at least two days to consume the monthly ceiling. That leaves time for an alert to be read and acted on. The calculation is recorded beside the deployment configuration and redone whenever a bound, the model, or its price changes.

## Edge protection

The service is deployed behind its hosting provider's edge, which terminates TLS and absorbs volumetric attacks before they reach the application. The edge enforces a request body limit of 32 KB and a connection rate limit per source. It does not present a challenge interstitial or fingerprint visitors by default; enabling either is an operator response to an active attack and is recorded.

The origin accepts connections only from the edge. The application takes the client's address only from the edge's own client-address header, and only on connections from the edge's published address ranges; any other forwarding header is ignored. Without this, either every visitor would share the edge's address or an attacker could set their own.

Because the edge terminates TLS, it sees every message, answer, access code, and sign-in code in plaintext, not only network addresses. It is a processor named in the privacy notice under [#40](https://github.com/Finntegrate/tapio/issues/40), and where it processes traffic is part of choosing it ([#44](https://github.com/Finntegrate/tapio/issues/44)).

## Request bounds

Applied before a turn runs and enforced during it. Initial values are configuration.

| Bound | Initial value | Enforced |
| --- | --- | --- |
| Request body | 32 KB | Edge and application |
| Message length | 4,000 characters | Client before sending, and request validation before any model call |
| Client-supplied history | None accepted | Request validation; see [conversation history](conversation-history.md#the-request) |
| Model input | `max_input_tokens`, as the sum of its components above | Server, when building each prompt |
| Output tokens | 1,024 | Passed to the provider on every call |
| Orchestration steps | 10 | Graph recursion limit |
| Model calls per turn | 7: three guardrail checks, each retried once, plus one answer or introduction | Counted at the model client |
| Tool calls per turn | 3 | Counted per turn |
| Tool result | 500 tokens | Truncated before the result enters a prompt, including error text that echoes arguments |
| Model call duration | 60 seconds | Timeout set on the model client, so a call that cannot be cancelled still ends |
| Turn duration | 120 seconds | Stopped, aborting in-flight calls; spend so far counts |

Every model the service builds, including the guardrail classifier's and the guardrail introduction's, is built through one factory that attaches a per-turn call counter, so a new call site cannot escape the count. Provider client libraries' own automatic retries are set to zero; retries the service makes are its own and are counted. The model-call bound is the worst case of the current graph and is revised whenever the graph changes.

A message over a bound gets a translated explanation, never a bare status code.

## Admission

A turn starts only when it has both a start token and a slot.

- **Turn-start rate.** A service-wide token bucket allows `turn_start_rate_per_minute` turns to start, with a burst of the same size. This is what bounds spend.
- **Concurrency limit.** At most `concurrency_limit` turns run at once, sized from the provider's own rate limits and response times. A turn holds its slot until its last upstream model call has returned or been aborted, not merely until its client disconnects or its handler is cancelled. Some calls run in worker threads that ignore cancellation, so the model-call timeout is what guarantees the call ends: a slot is held for at most the turn duration plus one model-call timeout, and `concurrency_limit` is sized with that tail included.
- **One per session.** A session runs at most one turn at a time. A second request from the same session while a turn is running is refused with "Still answering your last message", and the client prevents it from being sent.
- **Per-code share.** The sessions of one code hold at most `max_share` of the slots at once, and the code's turns stop starting once it reaches `max_turns_per_day`.

A request that cannot start yet joins a queue. While it waits, the stream sends a `queued` event and the interface shows that the guide will answer in a moment. When a start token and a slot are both free, the queue starts the oldest waiting request whose code is under its share, so one code's backlog never holds up another code's users.

The queue holds at most `queue_limit` requests, of which one code's sessions may hold at most `max_share`, so a code at its share cannot fill the queue and turn away other codes' users. No request waits longer than 20 seconds. Past either bound the request is refused with a plain busy message and the emergency line, and the person's text stays in the input so retrying needs no retyping.

## Rate limits

Session and network-bucket limits are held in memory and reset on restart, which is acceptable for a single-process beta. Per-code limits are in the store, above.

| Scope | Limit | Initial value |
| --- | --- | --- |
| Session | Turns, as a token bucket | Burst of 5, refilling 1 every 15 seconds |
| Session | Turns per rolling day | 200 |
| Network bucket | Code attempts | 60 per minute, 600 per hour |
| Network bucket | Sign-in code requests | 20 per hour |
| Network bucket | Turns | 120 per minute |

The session limits sit well above a person reading and replying. The network bucket's limits are high on purpose, so that a reception centre, a partner's workshop, or a mobile carrier is not affected; they exist to stop one machine running many sessions flat out.

A network bucket is an HMAC of the full IPv4 address, or of the IPv6 /64 prefix, under a key that is generated in memory, rotated daily, and never stored. Rotation resets every bucket, which is accepted. A bucket value is held in memory with a time-to-live of at most 24 hours, is never written to a log, an account, a conversation, or a partner report, and is never joined to any of them.

A request over a rate limit is refused, not slowed, with a message that says plainly what happened and when to try again, never implies wrongdoing, and carries the emergency line. Existing sessions are not ended.

## Tools and the kill switch

Metered and paid tools are disabled during the beta ([#17](https://github.com/Finntegrate/tapio/issues/17)). Only free tools are registered.

The service has an `open` flag, stored in the identity store and changed with the operator command, read with a cache of at most 5 seconds. When it is false, the service is in the closed state.

### Closed state

No turn runs. The interface shows a fixed, translated message, stored with the other user-facing strings and never generated, saying that Tapio is temporarily unavailable, with the emergency line and links to the official sources the guides draw on. The same state is entered when the provider refuses calls for exceeding its limit.

## Failure modes

| Case | Behaviour |
| --- | --- |
| Provider spend limit reached | Closed state until the period resets or the operator acts |
| Provider rate-limited or unavailable | The turn fails with a plain retry message and the emergency line; its slot is released when the call ends |
| Store unreadable | No turns run and no sessions are admitted; the closed message is shown |
| Queue wait exceeds its bound | Busy message with the emergency line; text stays in the input |
| Turn exceeds a bound before an answer | Stopped; spend so far counts; the person is told the answer could not be completed, with the emergency line |
| Turn exceeds a bound after a crisis or legal-sensitive match | Fixed resources are delivered and the turn completes |
| Client disconnects mid-turn | The turn runs to completion within its bounds and keeps its slot until its model calls end |
| Process restart | In-memory limits and the queue reset; per-code counters, sessions, and conversations persist |
| Shared network at a bucket limit | Requests over the limit are refused with a retry time; sessions are not ended |

## Observability and alerting

Recorded per turn, with no message content and no caller identity: guide, model, model calls, input and output tokens, tool calls, queue wait, outcome. Recorded per code, by `code_id`: sessions admitted and turns per day. Per-code figures are for Finntegrate operators only. Exported with the other operational metrics ([#37](https://github.com/Finntegrate/tapio/issues/37), [#38](https://github.com/Finntegrate/tapio/issues/38)).

Alerts to Finntegrate operators:

- Spend at 50% and 80% of the ceiling, and daily spend above the even daily share
- Queue waits regularly above a few seconds, which means the turn-start rate or concurrency limit is too low for real use
- A code admitting sessions or starting turns faster than its usual rate, or reaching a daily limit
- Failed code attempts above baseline
- Any turn reaching the model-call bound, which means either an attack or a graph change the bound has not caught up with
- Any closed-state transition

## Testing

- Request bounds: an oversized body, an over-long message, and a request carrying history are rejected before any model call, with a translated explanation.
- Model calls: a call made through any model the service builds, including the guardrail classifier and introduction, is counted; a turn with every guardrail check retried completes within the bound; provider client retries are off.
- Loops: a graph that would exceed its step, model-call, or tool-call bound is stopped at the bound.
- Spend bound: with clients that disconnect immediately after starting, turns start no faster than the turn-start rate, and no slot is released before its upstream call ends.
- Admission: with more concurrent requests than slots, at most `concurrency_limit` turns run, waiting requests receive a `queued` event, and a session cannot hold two slots.
- Fairness: one code's sessions cannot hold more than `max_share` of slots or of queue positions, or start more than `max_turns_per_day` turns, and another code's queued request starts ahead of them.
- Tail: a model call that ignores cancellation ends at the model-call timeout, and its slot is released then.
- Tool results: a tool result longer than its bound, including an error echoing an oversized argument, is truncated before the next model call.
- Codes: unknown, stopped, expired, and exhausted codes produce byte-identical responses; ending a code's sessions refuses them on their next request; a new code restores an ended session with its conversations; normalization accepts case and hyphen variants.
- Entry form: attempts beyond the per-bucket limit are refused, and no code becomes unusable because of failed attempts against it.
- Client address: a forwarding header on a connection not from the edge is ignored.
- Emergency line: the access-code page, a refused code, a rate-limit refusal, a busy refusal, the closed state, and a turn stopped by a bound all contain it; a turn matched as `crisis` that then hits the duration bound still delivers its resources.
- Closed state: the kill switch and a provider limit refusal both produce the fixed closed message.
- Privacy: no log line, metric, or alert contains a network address, a bucket value, a plain code, or message content; a test asserts this against captured output of admission and chat flows.
- Shared networks: many sessions behind one bucket at ordinary use rates, and thirty code entries with typos within a minute, are not limited.

## Later stages

The beta controls are sufficient while three conditions hold: admission requires a code, no paid or metered tool is enabled, and the service runs as one process. Each change below requires its controls first.

| Change | Controls required first |
| --- | --- |
| Admission without codes | In-application spend ceiling with staged degradation; friction on session creation |
| Paid or metered tools enabled | Cost-unit metering; tools gated by principal tier |
| Registered accounts and partner reporting | Per-tier budgets; reserved capacity so one population cannot exhaust another; partner allocations |
| More than one process | Limiter, queue, and rate-limit state in a shared store |

**In-application spend ceiling.** Spend is metered per turn from provider usage, against a daily and monthly budget set below the provider ceiling. As spend approaches the budget the service degrades in order: paid tools off, then a cheaper model or retrieval-only answers with new anonymous sessions declined, then closed. A handler that cannot read the spend state assumes the more restrictive state.

**Cost units.** Limits count priced model tokens plus a fixed price per paid tool call, from configuration, so a limit means the same thing whatever a request costs.

**Session creation friction.** A small proof-of-work challenge, solved by the browser without user action, issued by the service itself so no third party learns of the visit. Difficulty rises with load and is capped so that a low-end phone completes it in a few seconds, with a non-timing path for assistive technology.

**Per-tier budgets and reservations.** Anonymous, registered, and partner principals have separate budgets, a share of capacity is reserved for registered principals, and a partner's ceiling draws only on its own allocation.

## Delivery

The service does not accept public traffic before these are in place:

1. Server-held history, with its legal basis and impact assessment settled ([conversation history](conversation-history.md#delivery))
2. Request bounds, with model calls counted at the model client
3. Turn-start rate, concurrency limit, and the fair queue
4. Access codes, the admission endpoint, and per-code limits
5. The emergency line on every refusal surface
6. Provider spend ceiling and alerts, edge protection with client-address handling, and the kill switch ([#44](https://github.com/Finntegrate/tapio/issues/44))
7. Rate limits ([#32](https://github.com/Finntegrate/tapio/issues/32))
